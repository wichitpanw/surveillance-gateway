Surveillance Gateway Edge · Camera onboarding · behind the scenes

Camera onboarding backend

What the system does after you press Add Camera, by connection type and brand, and where playback for those cameras comes from. Based on the code running at the current build (server/server.js, server/vms/*, server/gateway/go2rtc-sync.js, server/gateway/playback.js)

Edge adds cameras · Regional adds Edge · Central adds Regional

Every route that adds cameras carries edgeOnly and requires the device.manage permission. Upper tiers see cameras only by importing the whole child node (rows of type edge_relay) · every path must state a matching province and district

RTSP comes from the device, never guessed

Video URLs come from ONVIF, LAPI or a VMS that actually answered. Brand URL templates are used only for single cameras where ONVIF fails

Every path ends at one point

INSERT into the cameras table, then call syncCamerasToStreamCore, which issues the Global ID and creates the stream in go2rtc

Overview

3 routes, one destination

One form (CameraModal.jsx) offers 5 Connection Types: Manual RTSP, ONVIF Camera, ONVIF NVR, API (Uniview LAPI, AXIS S30), VMS (Milestone Bridge, Digifort, Dahua DSS Pro at the Edge · Edge Gateway at the Regional). Every type requires a province and district before saving. Each type hits a different route, and all converge on the cameras table

User screen route / step Data store Point every path must pass

Where the picture comes from

5 kinds of video source

The edge does not always connect to every camera head directly. In some cases video comes from an NVR or VMS that already holds the camera. What the edge stores is the RTSP URL of that source, and the edge go2rtc opens a line to pull the video

Type by type · what the edge talks to and what comes back

How the edge imports each kind of camera

In each card, the steps follow the order the edge actually performs after the button press. Example URLs hide the password, and orange marks the part that varies by camera or channel

manual

Manual RTSP

Use when the camera has no ONVIF or ONVIF is broken (e.g. some Dahua models)
User enters
Main URL, sub URL (optional), brand, name, group, province + district (required)
Edge talks to
Does not contact the camera when saving
  1. Accepts the URL as typed; does not check that it opens
  2. Empty sub: the system uses the same URL as main (Live Wall will transcode the full-size picture)
  3. INSERT type=manual, then go2rtc tries to open the line when someone watches
rtsp://user:****@<ip>:554/<path the user knows>
onvif_cam

ONVIF Camera

Single camera reachable from the edge directly over LAN / VPN
User enters
IP, ONVIF port (usually 80), RTSP port (554), user/pass, brand
Edge talks to
ONVIF (SOAP over HTTP) at the camera /onvif/device_service
  1. Connects over http, then tries https if that fails (some routers forward only HTTPS)
  2. GetProfiles + GetStreamUri per profile. If a camera behind NAT answers an internal address, the system substitutes the host that actually connects
  3. Groups profiles by VideoSource; main = highest resolution, sub = next stream, skipping MJPEG
  4. Puts user:pass into the URL and keeps the profile token for PTZ and snapshots
  5. If ONVIF fails entirely, uses the brand URL template with the RTSP port entered
rtsp://user:****@<ip>:554/<path the camera returns in GetStreamUri>
onvif_nvr

ONVIF NVR

Any NVR brand with ONVIF enabled · adds many channels at once
User enters
NVR IP, ONVIF port, RTSP port, user/pass, brand, name prefix (optional)
Edge talks to
NVR ONVIF (retries twice because NVRs over WAN are slow)
  1. GetProfiles returns profiles of channels that have video; GetVideoSources returns the full channel list including channels that are down
  2. Groups into channels, reads the channel number from the URL the NVR returns, in NVR order
  3. Channels without a profile show OFFLINE with no URL; already-added channels are marked ADDED
  4. After selection, bulk-add names them <prefix> CH n (<channel name>) or uses the name from ONVIF
Hikvision: …/Streaming/Channels/<channel>01 · 02
Dahua: …?channel=<channel>&subtype=0 · 1
Uniview: …/unicast/c<channel>/s0 · s1/live
onvif_nvr + nvr_channel

API · Uniview LAPI

Uniview NVR when you want real channel names and to add channels that are down
User enters
Same as ONVIF NVR + API port (LAPI HTTP)
Edge talks to
LAPI (HTTP Digest) and ONVIF of the same NVR
  1. GET /LAPI/V1.0/Channels/System/ChannelDetailInfos returns ID, Name, Status of every channel (unconfigured channels dropped)
  2. Queries ONVIF separately for RTSP; if ONVIF fails, the list from LAPI is still returned
  3. Matches the LAPI ID only to the c<channel> number in the ONVIF URL; never invents URLs
  4. Channels that are down can be added, as rows waiting for video that have a channel number but no RTSP
  5. The edge re-queries ONVIF 15 seconds after adding and every 2 minutes, then fills the URL into the same row once available
Channel name: from LAPI (name set in the NVR)
Video: rtsp://…/unicast/c<ID>/s0/live
onvif_nvr · axis

API · AXIS S30

AXIS S30 recorder with cameras paired · adds many channels, no camera IP needed
User enters
S30 IP, API port (default 443), RTSP port, recorder web account · the ONVIF port field is unused
Edge talks to
Recorder VAPIX over HTTPS (self-signed recorder certificate) with Basic auth

digifort_relay

VMS · Digifort

Site where Digifort holds the cameras and we do not know the camera IPs
User enters
Digifort host address, API port 8601, RTSP 554, user/pass
Edge talks to
Digifort HTTP API (ResponseFormat=JSON)
  1. /Interface/Cameras/GetCameras, GetStatus, GetGroups, /Interface/Server/GetInfo called once, no retry
  2. The user selects cameras and presses import; the edge re-queries the list to confirm the password before writing the DB
  3. Creates a camera_sources row with the password sealed by the key vault

dss_relay

VMS · Dahua DSS Pro

Site that aggregates cameras in DSS Pro · tested with V8.5.0
User enters
DSS address, port 443 (HTTPS), user/pass · no RTSP port to enter
Edge talks to
DSS OpenAPI (/brms/api/v1.0/…), two-step login, then renews the session every 20 seconds
  1. /api/vms/probe logs in and walks the channels of every device (device/channel/list) for channel name, group, IP and status, then logs out · called once, no retry
  2. The list holds hundreds of channels; the form has a filter box and select all / none buttons (applies only to what is visible)
  3. /api/vms/import re-confirms the password and list before writing the DB, then stores the password sealed in camera_sources
  4. Each camera gets source_ref = the DSS channelId and a local relay URL; no token or password in the DB
  5. Online state comes from the channel status field, polled from DSS every 60 seconds, not TCP
rtsp://127.0.0.1:<gateway port + 26>/dss/<camera id>/<main|sub>
edge_relay

Edge → Regional → Central

Regional imports every camera of one Edge · Central imports a whole Regional the same way
User enters
pull: child node address and API port + API key · link: nothing to enter, the child node connects up itself with a token · at the Regional, pick the province from a dropdown and add a Remark identifying the site (one province can have several Edges)
Upper tier talks to
The child node /api/v1, and SSE /api/v1/events for state
  1. Requests the camera list and stream addresses from the child node (no camera passwords included)
  2. INSERT cam_edge_<node>_<id> using the Global ID issued by the Edge (passed through unchanged at every tier) · the Regional sends its catalog up to Central itself
  3. pull: the URL points at the child node go2rtc with a go2rtc account (uses the _raw line when available)
  4. link: whenever someone watches, the upper tier tells the child node to push video into <id>_in; with no viewer for over 60 seconds it orders a stop, nested in order Central → Regional → Edge
  5. Reviews names, coordinates and streams every 10 minutes
pull: rtsp://<go2rtc account>@<child node>:<go2rtc RTSP port>/<id>_raw
link: stream <id>_in on the upper tier

Many channels · ONVIF NVR · Uniview API · AXIS S30 · Milestone Bridge

Scan first, pick channels, then add the batch

These four types share the same two-beat flow: press Scan Channels to get the channel list, select, then press Import Channels. Only the scan method differs

Channels offline at scan time

Some NVR models drop channels without video from GetProfiles, but GetVideoSources still reports them (Framerate 0). The system shows them as OFFLINE and does not invent a URL. Rescan when the camera is back; the same channel will not produce a duplicate row

Uniview API can add while offline

The row enters the DB with a channel number (nvr_channel) but no RTSP yet. The system re-queries ONVIF after 15 seconds and periodically, then fills the URL into the same row, so id, Global ID, pin and permissions are not lost

Rescan = sub update

For channels already added whose main matches, the system rewrites sub to what the NVR reports now (refreshExistingNvrSubs); main is not touched

AXIS S30 differs from the other three

No ONVIF at all. On import the edge re-queries the recorder and builds URLs only from confirmed ids (an id not in the list = 400). Video goes through the one recorder RTSP port for every channel, so sub equals main

Via a relay · Digifort and child nodes

Cameras that do not talk to the camera head directly

These two types tie a camera to a row in the camera_sources table. The source is a VMS machine or an Edge / Regional machine, not the camera. The key of each camera is source_ref

External system route Child node link Row in cameras

Who owns the data

The Edge owns name, brand, coordinates, province, district, Global ID and stream address; resync overwrites them every round. Central owns the display groups, wall layouts and per-region/province permissions. Pinning at Central or a Regional therefore gets 403 · if a camera has no province, the Dashboard shows the source Regional region instead

How video travels

pull: the upper tier pulls RTSP straight from the child go2rtc · link: the child uses ffmpeg to push video into the <id>_in stream that the upper tier created in advance (go2rtc 1.9.14 cannot push out as rtsp:// itself) · one camera crosses a link between tiers only once, however many people watch

Why it never deletes cameras itself

A source that answers incompletely for a moment would turn into a mass delete with pins and permissions, which a new import cannot restore. So the system reports which ones are missing and lets a person decide

Via a relay · Dahua DSS Pro

A DSS live URL works only once

Unlike Digifort, DSS hands out a URL with a token that opens only once (reuse or concurrent connection returns 401), but go2rtc needs a fixed URL it can reconnect to repeatedly. So the edge sets up a local RTSP relay for go2rtc to connect to, and the relay asks DSS for a fresh URL on every connection

External system Edge component Relay that requests fresh URLs ── Line carrying a DSS token

What the relay rewrites on the way

Outbound, a URI starting with the local address is replaced by the real DSS URL. On the way back, Content-Base is changed back to the local address, so go2rtc sees a single URL throughout. Video data passes straight through with backpressure. If a URL cannot be obtained from DSS, the relay closes the connection and go2rtc reconnects by itself

Accounts can be locked

DSS locks an account after several wrong passwords, so the edge stops the moment a login fails because of the password and remembers that state until a person enters a new password (re-sync with a password). It never retries by itself

Camera state comes from DSS

Our TCP reaches only the local relay, which always answers. So the edge asks DSS every 60 seconds and writes reachable itself, the same as for cameras from an edge · re-sync does not delete cameras that vanish from DSS but reports them for a person to decide

Playback · pulled from the device

Where playback comes from

The system does not record video itself (the edge recorder was removed on 2026-09-28). When someone asks, the edge queries the recorded ranges and pulls video from the device or VMS that holds it. The path is decided by the type and brand of the camera as added (server/vms/device-playback.js)

It finds the camera recording by the VideoSource token first, then by name. Known limitation

From viewer to device

How a request travels

The edge holds the camera passwords and can reach devices on the LAN, so playback is always read at the edge. Central and Regional are only a pass-through for edge_relay cameras (nested requests Central → Regional → Edge). With a pull edge the upper tier connects in. A link edge is behind NAT and the upper tier cannot connect in, so the direction reverses: the edge uploads the video upward · Clients in the region can point at the Regional directly without passing through Central

Viewer Central / Regional · pull edge link edge Customer site ── Reversed path (edge uploads upward)

Permission separate from live view

The recordings, playback.mp4 and frame.jpg routes require allow_playback on the API key, because playback is evidence · playback-token issues a token that lets a native client open an MP4 only for cameras within the key scope

What a request looks like

recordings requires from and to (ISO-8601, to > from) · playback.mp4 requires start and a duration of 1–3600 seconds · video=h264 transcodes for browsers; omitted = the camera original codec · the real time of the first frame is in the X-Playback-Start header

Concurrency ceiling at the edge

2 per camera · 8 per device address · 16 per edge. Beyond that it answers 429, because an NVR accepts only a limited number of replay sessions and each ffmpeg consumes edge CPU

Three nested tiers need ordered timeouts

The outer tier timeout must exceed the inner one by at least 2 seconds, otherwise the outer tier fails first · closing the window midway must close the lower-tier pipes too. This passed testing against a simulated source, but has not yet been confirmed against every real NVR type on the three-tier topology

Why a link waits only 45 seconds

An upload session works once and must come from the owning edge. If it does not arrive within 45 seconds (LINK_PLAYBACK_WAIT_MS) the viewer gets 504 · set longer than a normal RPC because Profile G may search recordings in several rounds, taking over ten seconds

Area · province and district

Every path must state the area before saving

The Edge enforces a matching province and district when adding a camera, by any method. The API rejects blanks and mismatched pairs with 400 before writing anything to the database. The system does not guess a province for existing cameras

required

When adding a camera

The form has a province dropdown, then loads the districts under that province (GET /api/regions)
  1. Covers POST /api/cameras, /api/cameras/bulk-add (NVR, Uniview, AXIS S30, Milestone) and /api/vms/import (Digifort, DSS Pro)
  2. validateRequiredRegion(province_code, district_code) checks that the district really belongs to the province; failure = 400
  3. Once it passes, INSERT the camera row, then saveCameraRegion writes the area before sync issues the Global ID
PATCH /api/cameras/region

Edit the area for a whole group

Only at the Edge that owns the cameras · accepts cameras selected across groups
Accepts
ids 1–1000 cameras + province + district
Rejects
A list containing a camera not found (404 before writing) · edge_relay cameras (403) · cameras outside the user scope (403)
  1. Checks the device.manage permission and ownership of every camera
  2. A single UPDATE for the whole batch · Global ID and coordinates are unchanged
  3. Clears the role cache by region, then catalogSoon() sends the catalog up to the Regional and Central immediately
upper tiers

What Regional and Central do with the area

Receive area data from the Edge and never edit it
  • The Regional rejects Edges outside the region number block, and catalogs containing provinces outside the region
  • Central uses the province for per-region/province role permissions; new cameras in the area become visible automatically without ticking
  • Existing cameras with no province need a real area chosen at the Edge, then wait for sync to the upper tiers

After saving · the same for every type

What happens after the INSERT

  • Global ID format TH-<province>-<node no.>-<seq>. The Edge issues it once on the first sync round, so the province must be saved first (saveCameraRegion). Sequence numbers are never reused even after a camera is deleted. Regional and Central pass the original value through every tier and never reissue it · district, site and Remark are location data and are not in the ID
  • go2rtc gets 3 lines per camera: <id> (main) and <id>_sub, always transcoded to H.264 through ffmpeg because go2rtc 1.9.14 crashes when sending H.265 out over MSE · <id>_raw is a passthrough with #backchannel=0 for clients that decode H.265 themselves
  • Updates go through REST without restarting go2rtc, so adding one camera never cuts the video of other cameras
  • How the upper tiers learn of cameras: the Edge sends its catalog up to the Regional, and the Regional sends it up to Central every 10 minutes, with an immediate notice when a camera changes (two nested tiers can lag up to ~20 minutes without the immediate notice) · reachable on a branch whose link is down is null, not false
