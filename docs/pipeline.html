The pipeline, step by step

One camera passes through 8 steps before its picture reaches a viewer. The top half prepares the picture, almost entirely at the edge (register → sync catalog → ingest). The bottom half is delivery at central (authorise → sign token → deliver → watch). Step 04 is the pivot: central is the only place that transcodes, and only the line browsers need.

What each step does

01

Register

Edge admin · edge web UI

Cameras can be added 5 ways: manual RTSP, single-camera ONVIF, NVR scan via ONVIF, Uniview API, and VMS (Digifort) · central cannot add cameras itself (403)

The system keeps main = stream 1 and sub = stream 2, never stream 3 · each camera gets a global ID TH-province-node-seq that never changes for its lifetime · camera passwords live only at the edge

server/server.js (resolveOnvifStreams · groupOnvifProfiles) · server/gateway/identity.js

02

Sync

edge → central

pull: central reads the edge /api/v1 with an API key issued by the edge (health every 60 s, sync every 10 min) · link: the edge opens a WebSocket to /api/edge-link itself, for edges behind NAT

Name, coordinates, province and reachable state always come from the edge; central owns only display groups, wall layouts and permissions

server/vms/edge-source.js · server/vms/edge-link-server.js · edge-link-client.js

03

Ingest

edge go2rtc ← camera

The edge opens RTSP to the camera only while someone is watching, then passes the _raw line to central untranscoded: with pull, central go2rtc fetches it; with link, the edge ffmpeg pushes (-c copy -an) to the <id>_in stream that central prepared

The edge does not transcode, so it needs no GPU; a mini PC or Raspberry Pi 5 is enough

server/gateway/go2rtc-sync.js (rawSourceFor) · server/vms/edge-link-client.js

04

Normalise

central go2rtc · GPU NVENC

The system pivot. Central builds two lines per camera: the normal line is forced to H.264 (#video=h264#hardware) for browsers, because go2rtc crashes when sending H.265 over MSE, and the _raw line passes the camera original codec through

Transcoding happens only while someone opens the H.264 line · the web Live page always uses the sub stream

server/gateway/go2rtc-sync.js (sourceFor · rawSourceFor)

05

Authorise

consumer → central /api/v1

Clients and external systems call /api/v1 with Authorization: Bearer <key> issued on the API Clients page. Each key is bound to camera-group scope and PTZ rights, filtered in SQL

Camera passwords never leave through the API: queries use whitelisted columns, no SELECT * · web users log in with a password stored as a scrypt hash

server/gateway/auth.js · server/gateway/index.js · server/shared/password.js

06

Sign

central gateway

GET /api/v1/cameras/:id/streams returns a URL with an HMAC token bound to a single stream, valid 5 minutes, checked only at open time

A token is needed because the <video> tag cannot send headers, and one token opens only the path it was signed for

server/gateway/stream-token.js · server/gateway/streams.js

07

Deliver

Node proxy :5173

Checks the token at /stream/<name>.mp4, then pipes fMP4 from go2rtc straight through; everything leaves through the single port 5173 · link cameras: if nobody is pushing yet, central sends stream.open to the edge and waits up to 8 seconds for video

Camera state goes out over SSE /api/v1/events (enabled · reachable · streaming)

server/server.js (requireStreamToken · proxyToStreamCore) · server/shared/camera-state.js

08

Watch

central web · Windows client

The Windows client plays mp4Raw (the original H.265 from the camera), decoded on the user GPU, with a 1–25 tile video wall and main/sub switching · the central web UI plays the H.264 line on the Live page (1/4/9/16 tiles + PTZ)

The client updates itself from /client-updates on the same central

client-windows/ · src/components/LiveWall.jsx · docs/CLIENT-RELEASES.md

Network hops — camera to screen (see architecture.html for the overview)

H1

Camera → edge

RTSP · ONVIF · site LAN

The edge always dials out to the camera; the camera never sends to us. ONVIF is used for scanning and reading profiles, RTSP for pulling video. The edge checks whether the camera answers (TCP to the RTSP port) every 15 seconds

Video is connected only while someone watches; no viewer = no video connection to the camera

H2

Edge → central

pull :5173 + RTSP :8555 · or link ws + push

pull: central connects to the edge with an API key and fetches RTSP _raw from the edge go2rtc · link: the edge opens the WebSocket itself, trying central addresses in order (LAN, VPN, NAT-translated IP), then pushes video to the central RTSP

No TLS yet: tokens and RTSP credentials travel unencrypted, so use only on a LAN or Tailscale · edge update packages are signed with ed25519

H3

Inside central

HOST · 203.0.113.80

go2rtc (:1984 API, :8555 RTSP) receives video from the edge and hands it to the Node gateway over localhost. Node checks the token before every outgoing video

Edge 001 runs on the same host, on ports 5273 / 1994 / 8565

H4

Central → user

HTTP :5173 · LAN / Tailscale

Users enter through the single port 5173: web UI, API, video, client installer and edge install kit. On the LAN use 203.0.113.80; from outside, enter via the central Tailscale address

Users never connect to cameras or edges directly and never know camera passwords

H5

Side door

RTSP :8555

Port 8555 connects directly to the central go2rtc without passing Node, so tokens are not checked. It has its own RTSP account (.rtsp-credentials.json) used by link edges and operations tooling

Open the firewall for this port and 1984 only to the IP ranges that need it
