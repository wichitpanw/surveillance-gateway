หน้านี้พาตาม "ภาพ 1 เส้น" ตั้งแต่เจ้าหน้าที่กดเพิ่มกล้องที่ Edge ไปจนภาพขึ้นจอ Windows Client ว่าข้อมูลถูกส่งผ่านโปรแกรมอะไร เครื่องไหน ด้วยโปรโตคอลอะไร และถูกแปลงรูปตรงไหนบ้าง อ่านเรียงจากบนลงล่างได้เลย ศัพท์ที่ไม่คุ้นดูที่ส่วนแรก

ก่อนเริ่ม: ศัพท์ที่ต้องรู้

กล้อง IP
กล้องที่ต่อสายแลน ส่งภาพเป็นข้อมูลดิจิทัลผ่านเครือข่ายได้ มีหมายเลข IP เหมือนคอมพิวเตอร์ เช่น 192.168.1.10
RTSP
"ภาษา" สำหรับขอดูภาพสดจากกล้อง (เหมือนกดเล่น/หยุด) หน้าตาที่อยู่ rtsp://user:pass@192.168.1.10/stream1 ตัวภาพวิ่งเป็นแพ็กเก็ต RTP
ONVIF
มาตรฐานกลางให้ถามกล้องยี่ห้อไหนก็ได้ว่า "มีช่องภาพอะไรบ้าง ที่อยู่ RTSP คืออะไร" และสั่งหมุนกล้อง (PTZ) ได้
โค้ดวิดีโอ (codec)
วิธีบีบอัดวิดีโอให้เล็กลง H.265 เล็กกว่า H.264 แต่เบราว์เซอร์เล่น H.265 ตรง ๆ ไม่ได้ ส่วนโปรแกรม Client ถอดได้ด้วยการ์ดจอ
แพ็กเก็ต (packet)
ก้อนข้อมูลเล็ก ๆ ที่ข้อมูลทุกอย่างถูกหั่นก่อนส่งผ่านเครือข่าย แต่ละชิ้นมีหัวบอกลำดับ ปลายทางเรียงกลับตามลำดับ
TCP
วิธีส่งแพ็กเก็ตที่รับประกันว่าครบและเรียงลำดับ ถ้าหายจะส่งซ้ำ ระบบนี้ใช้ TCP ทุกช่วงของภาพ
WebSocket
สายคุยสองทางที่เปิดค้างไว้ ใช้เป็น "สายคำสั่ง" ระหว่าง Edge – Regional – Central (HTTP ปกติถามแล้วตอบจบ ส่วนนี้ฝั่งไหนจะพูดก่อนก็ได้)
go2rtc
โปรแกรมตัวกลางรับและแจกจ่ายภาพ (stream core) ทุกเครื่องในระบบมีของตัวเอง ตัวมันเองไม่เก็บภาพ แค่ส่งผ่าน
ffmpeg
โปรแกรมเอนกประสงค์จัดการวิดีโอ ในระบบนี้ใช้ "ผลัก" ภาพขึ้นไปชั้นบน และใช้แปลงโค้ดเมื่อจำเป็น
fMP4
ไฟล์วิดีโอ MP4 แบบหั่นเป็นท่อน ๆ เล่นไปส่งไปได้โดยไม่ต้องรอไฟล์ครบ ใช้ส่งภาพสดผ่าน HTTP
copy กับ transcode
copy = ส่งต่อทั้งก้อนโดยไม่แกะ (เบามาก) · transcode = แกะออกเป็นภาพแล้วบีบใหม่ (กิน CPU/GPU) ระบบนี้พยายาม copy ให้มากที่สุด
NAT / firewall
ตัวกั้นที่ทำให้เครื่องภายนอกต่อเข้ามาหาเครื่องในไซต์ตรง ๆ ไม่ได้ จึงออกแบบให้ Edge เป็นฝ่ายต่อออกไปหาข้างบน
Global ID
เลขประจำกล้องที่ออกครั้งเดียวและไม่เปลี่ยน เช่น TH-10-101-00001 = ไทย – จังหวัด 10 – Edge 101 – กล้องลำดับที่ 1
token / API key
กุญแจแสดงตัวตน มีหลายชนิดตามหน้าที่ (ดูตารางท้ายหน้า) เช่น API key ของ Client, token เปิดภาพ 5 นาที

ภาพรวม: ห้าขั้นจากกล้องถึงผู้ใช้

ระบบมี 3 ชั้นตามพื้นที่: Edge (ไซต์/จังหวัด) → Regional (ภาค) → Central (ประเทศ) แต่ละชั้นคือโปรแกรมตัวเดียวกันที่ตั้งค่าบทบาทต่างกัน มี 3 กติกาที่ทำให้ระบบเป็นแบบนี้:

  1. 1
    Edge เป็นคนเพิ่มกล้อง — Edge ถือรหัสผ่านกล้อง ชั้นบนไม่เคยเห็นรหัสผ่านเลย
  2. 2
    ลูกต่อขึ้นหาแม่เสมอ — Edge เปิดสายขึ้นไปหา Regional (และ Regional ขึ้นไปหา Central) เพราะหน้างานอยู่หลัง NAT ต่อเข้าไปหาไม่ได้
  3. 3
    ภาพวิ่งเฉพาะตอนมีคนดู — ปกติมีแต่ข้อความเล็ก ๆ วิ่งในสายควบคุม ภาพจริงเริ่มวิ่งเมื่อมีคนกดดู และหยุดเมื่อไม่มีคนดู 60 วินาที

ขั้นที่ 1 — เจ้าหน้าที่เพิ่มกล้องที่ Edge

ทุกอย่างเริ่มที่ Edge เท่านั้น Regional และ Central ไม่มีปุ่มเพิ่มกล้อง (ระบบปิดทางนี้ไว้ที่ API เลย) เพราะรหัสผ่านกล้องของหน่วยงานต้องอยู่ที่ไซต์ ไม่ควรไปกองอยู่ส่วนกลาง

  1. 1
    เจ้าหน้าที่เปิดหน้าเว็บของ Edge (เช่น http://<IP ของ Edge>:5173) ไปที่ Cameras → Add Camera ใส่ IP ชื่อผู้ใช้ รหัสผ่านของกล้อง และ ต้องเลือกจังหวัดกับอำเภอ (บังคับ)
  2. 2
    Edge ถามกล้องผ่าน ONVIF ว่า "มีช่องภาพอะไรบ้าง" กล้องตอบกลับเป็นรายการ profile Edge จึงได้ URL RTSP ของ main (ภาพละเอียดสูง) และ sub (ภาพเล็ก ใช้ตอนดูหลายช่องพร้อมกัน) · ถ้าเพิ่มจาก NVR/VMS/RTSP ที่กรอกเอง วิธีถามจะต่างกันแต่ผลลัพธ์เหมือนกัน
  3. 3
    Edge บันทึกลงฐานข้อมูล SQLite ของตัวเอง: ชื่อ URL RTSP (มีรหัสผ่านกล้องฝังอยู่ — เก็บที่นี่ที่เดียว) จังหวัด/อำเภอ แล้วออก Global ID เช่น TH-10-101-00001 ครั้งเดียว ไม่เปลี่ยนอีกตลอดอายุกล้อง
  4. 4
    Edge สั่ง go2rtc ผ่าน REST ให้ลงทะเบียนสตรีมของกล้อง 4 เส้น: <id> (แปลงเป็น H.264 ไว้ให้เว็บ) <id>_sub <id>_raw (ส่งต่อตามโค้ดเดิมของกล้อง ไม่แปลง) และ <id>_sub_raw · ตอนนี้ยังไม่ได้ต่อกล้องจริง go2rtc จะต่อหากล้องก็ต่อเมื่อมีคนขอดู
  5. 5
    ทุก 15 วินาที Edge ลองต่อ TCP ไปยังพอร์ตของกล้อง (เหมือนเคาะประตูดูว่ามีคนอยู่ไหม) เพื่อรู้ว่ากล้องยังตอบหรือไม่ ได้สถานะ 3 ค่า: เปิดใช้อยู่ไหม · ติดต่อได้ไหม · กำลังมีคนดึงภาพไหม
  6. 6
    Edge ส่งรายชื่อกล้องขึ้น Regional ทันทีผ่านสาย WebSocket (ไม่ต้องรอรอบ 5 นาที) — เรื่องในขั้นถัดไป

ขั้นที่ 2 — รายชื่อกล้องและสถานะเดินทางขึ้นไปหา Central

ตรงนี้ยังไม่มีภาพวิดีโอวิ่งเลย มีแต่ข้อมูลข้อความเล็ก ๆ (JSON) ว่ามีกล้องอะไรบ้าง สถานะเป็นยังไง สายนี้คือ WebSocket ที่ Edge เปิดค้างไว้หนึ่งเส้นต่อ Regional หนึ่งตัว

  1. 1
    Edge "โทรออก" ไปที่ ws://<Regional>:5273/api/edge-link ส่ง hello (เลข node, รุ่นโปรแกรม, จังหวัดของตัวเอง) พร้อม link token — Edge เป็นฝ่ายเริ่มเสมอ จึงทะลุ NAT ได้โดยไม่ต้องเปิดพอร์ตขาเข้า
  2. 2
    Regional ตรวจ token และเลข node (Edge ในภาค Regional 100 ต้องใช้เลข 101–199) แล้วตอบ welcome สายนี้เปิดค้างไว้ ส่ง heartbeat ทุก 20 วินาที ถ้าเงียบเกินราว 60–70 วินาทีถือว่าสายตาย แล้ว Edge ต่อใหม่เอง
  3. 3
    Edge ส่ง catalog: ชื่อ Global ID จังหวัด พิกัด และ "มีสตรีมไหม" — ไม่มีรหัสผ่านกล้อง Regional เขียนแถวกล้องแบบ relay ลงฐานข้อมูล แล้วสร้างสตรีมเปล่าชื่อ <id>_in ใน go2rtc ของตัวเองเพื่อรอรับภาพ (ส่งซ้ำทุก 5 นาทีและเมื่อมีการแก้ไข)
  4. 4
    Regional ทำตัวเป็น "Edge" ของ Central: ส่ง catalog รวมกล้องทั้งภาคขึ้นไป พร้อม Global ID เดิม Central ทำแบบเดียวกัน
  5. 5
    กล้องหลุดหรือกลับมา → Edge ส่ง camera_state ทันที ไม่รอรอบ
  6. 6
    Regional ส่งต่อให้ Central — ชั้นบนเห็นสถานะภายในไม่กี่วินาที
  7. 7
    Windows Client ขอรายชื่อกล้องด้วย GET /api/v1/cameras พร้อม API key (Authorization: Bearer sgw_…)
  8. 8
    Central ตอบ JSON รายชื่อกล้อง + สถานะ เฉพาะกล้องที่ key นั้นมีสิทธิ์เห็น · ถ้าสายของ Edge ขาด สถานะกล้องเป็น "ไม่ทราบ" (ไม่ใช่ "ดับ") เพราะ Central แยกไม่ได้ว่ากล้องดับหรือแค่สายขาด

ขั้นที่ 3 — ภาพวิ่งผ่านอะไรบ้างจากกล้องถึงจอ

นี่คือหัวใจของระบบ ภาพ 1 เส้นผ่าน 8 จุด เจ็ดช่วง ลูกศรเข้มคือการส่งข้ามเครื่อง ลูกศรอ่อนคือส่งต่อภายในเครื่องเดียวกัน ตัวเลขในวงกลมตรงกับคำอธิบายทางขวา สังเกตว่าตลอดทางจากกล้องถึง Central ไม่มีการแปลงโค้ดเลย — แพ็กเก็ตถูกคัดลอกต่อ ๆ กันไป

ภาพ 1 เฟรมมีชีวิตอย่างไร

ภาพวิดีโอคือภาพนิ่งหลายสิบภาพต่อวินาที ภาพนิ่งแต่ละภาพ (เฟรม) เดินทางตามขั้นตอนนี้ — ช่วง 3–5 คือช่วงที่เครือข่ายของเราทำงาน

ตัวอย่างจริง: ที่อยู่ RTSP เปลี่ยนไปยังไงจากกล้องถึงผู้ชม

กล้องตัวเดียวกัน ตามดูที่อยู่ (URL) ที่ถูกใช้ในแต่ละช่วง ส่วนที่มีกรอบสีส้มคือส่วนที่เปลี่ยนจากแถวก่อนหน้า · สีน้ำเงินตัวหนา = เครื่อง:พอร์ต · สีน้ำตาล = ชื่อผู้ใช้:รหัสผ่านในที่อยู่ (ตัวอย่างนี้เป็นรหัสสมมติ)

ขั้นที่ 4 — ใครสั่งให้ภาพเริ่มวิ่งและหยุดวิ่ง

ภาพไม่วิ่งตลอดเวลา ถ้าไม่มีใครดู ข้อมูลภาพไม่ข้ามเครือข่ายเลย (10,000 กล้องไม่ได้แปลว่า 10,000 สตรีมวิ่งอยู่) ภาพเริ่มวิ่งเมื่อมีคนขอดู แล้ว Central สั่งผ่านสาย WebSocket ลงไปทีละชั้น

  1. 1
    Client ขอ URL ของภาพกล้องตัวที่เลือก (/api/v1/cameras/:id/streams)
  2. 2
    Central ตอบ URL แบบ …/stream/<id>_raw.mp4?t=… ที่มี stream token ผูกกับกล้องตัวนี้ อายุราว 5 นาที
  3. 3
    Client ขอเปิด URL นั้น Central ตรวจ token แล้วพบว่าภาพยังไม่มา จึงสั่งชั้นล่างให้ส่งภาพมาก่อน (รอได้ไม่เกิน 8 วินาที ถ้าไม่ทันผู้เล่นจะได้จอดำแล้วลองใหม่เอง)
  4. 4
    Central สั่ง Regional ผ่าน WebSocket: stream.open พร้อมบอกว่าให้ push ไปที่ไหน ชื่ออะไร ด้วยบัญชีไหน
  5. 5
    Regional ยังไม่มีภาพเหมือนกัน จึงสั่ง Edge ต่อ — stream.open อีกชั้น
  6. 6
    Edge เปิด ffmpeg อ่านสตรีม <id>_raw ใน go2rtc ของตัวเอง ทำให้ go2rtc เพิ่งมีคนอ่าน จึงต่อ RTSP ไปขอภาพจากกล้อง
  7. 7
    กล้องส่งวิดีโอ RTP (H.265) กลับมา
  8. 8
    ffmpeg ที่ Edge ผลักแพ็กเก็ตขึ้นสตรีม <id>_in ของ Regional แบบ -c copy
  9. 9
    Regional เห็นว่ามีภาพเข้า จึงเปิด ffmpeg ของตัวเองผลักต่อขึ้น Central
  10. 10
    Central เห็นภาพเข้า ห่อเป็น fMP4 ส่งทาง HTTP ที่ผู้เล่นค้างรออยู่ — ภาพขึ้นจอ
  11. 11
    ผู้ใช้ปิดช่องภาพ ถ้าไม่มีใครอ่านสตรีมนั้นครบ 60 วินาที Central สั่ง stream.close (ตัวตรวจรอบทุก 20 วินาที)
  12. 12
    Regional ปิดต่อถ้าไม่มีผู้ชมในภาคแล้ว → Edge หยุด ffmpeg → go2rtc ตัดการต่อกล้อง กล้องกลับมาเงียบเหมือนเดิม

ขั้นที่ 5 — ปลายทางสองแบบ: Client ได้ภาพดิบ เว็บได้ภาพที่แปลงแล้ว

ที่ Central ภาพกล้องตัวเดียวกันมี 2 สตรีมให้เลือก ผู้ขอเป็นคนเลือกจากชื่อใน URL (ชื่อที่ลงท้าย _raw หรือไม่)

  • Windows Client เลือกเส้น _raw: รับ H.265 ตรง ๆ แล้วใช้ GPU ของเครื่องตัวเองถอดรหัส (libVLC) ไม่ผ่านการแปลงใด ๆ — เซิร์ฟเวอร์เบา ภาพหน่วงน้อย ดูหลายช่องพร้อมกันได้
  • เว็บเบราว์เซอร์ (หน้า Live) เลือกเส้นปกติ: เบราว์เซอร์เล่น H.265 ผ่าน MSE ไม่ได้ Central จึงให้ ffmpeg + การ์ดจอแปลงเป็น H.264 ก่อน ทุกช่องที่เปิดดูกิน 1 งานแปลงโค้ด ผู้ชมเว็บพร้อมกันจำนวนมากจึงต้องระวัง

ข้อควรรู้

  • ยังไม่มี TLS: สาย ws:// rtsp:// http:// ทุกเส้นวิ่งแบบไม่เข้ารหัส ต้องใช้ผ่าน LAN / VPN / Tailscale เท่านั้น ส่วนแพ็กเกจอัปเดตโปรแกรมกันการปลอมด้วยลายเซ็น ed25519
  • ระบบไม่บันทึกวิดีโอเอง: ภาพย้อนหลังดึงจากเครื่องบันทึกของกล้อง/NVR/VMS ผ่านสายเดียวกัน ตอนมีคนขอดูเท่านั้น
  • Central ล่ม: Client ที่ตั้งชี้ Regional ของภาคตัวเองยังดูภาพในภาคได้ (Client ยังไม่สลับให้อัตโนมัติ ต้องเลือกเอง)
  • สายของ Edge ขาด: กล้องขึ้น "ไม่ทราบสถานะ" และ Edge ต่อกลับเองอัตโนมัติ ไม่ต้องแอดกล้องใหม่ Global ID เดิมคงอยู่
  • เส้นทางอื่นที่ไม่ได้ลงในหน้านี้: สั่ง PTZ (ผ่านสาย WebSocket เดียวกัน) · ดูย้อนหลัง · เสียงจากกล้อง (เปิดรายกล้องที่ Edge) · AI event + ภาพประกอบ — ดู docs/EDGE-PLAN.md และ docs/CAMERA-AUDIO.md
